# 08 · 统一身份与认证

> D365 和 M365 共享同一个 Entra ID（Azure AD）——这是所有集成的基础。本章讲解统一身份体系下的认证机制、单点登录（SSO）实现、以及跨系统调用的权限管理。

## 1. 统一身份体系概览

### 1.1 一个租户，多个服务

```
┌─────────────────────────────────────────┐
│           Entra ID 租户                  │
│         (yourcompany.onmicrosoft.com)    │
│                                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │  用户    │  │  应用    │  │  组     │ │
│  │  Accounts│  │  Apps   │  │  Groups │ │
│  └────┬────┘  └────┬────┘  └────┬────┘ │
│       │            │            │       │
│       └────────────┼────────────┘       │
│                    │                    │
│         ┌──────────┴──────────┐         │
│         │   OAuth 2.0 / OIDC  │         │
│         │   认证 & 授权协议    │         │
│         └──────────┬──────────┘         │
│                    │                    │
│    ┌───────────────┼───────────────┐    │
│    │               │               │    │
│  ┌─┴──┐       ┌────┴───┐     ┌────┴──┐ │
│  │D365│       │ M365   │     │自定义  │ │
│  │CRM │       │Services│     │Apps   │ │
│  └────┘       └────────┘     └───────┘ │
└─────────────────────────────────────────┘
```

### 1.2 D365 开发者已熟悉的身份概念

| 概念 | 你在 D365 里怎么用 | 在 M365 里完全一样 |
|---|---|---|
| 用户（User） | CRM 里的 SystemUser | Entra ID 里的 User，同一个对象 |
| 应用注册（App Registration） | 给外部应用访问 CRM 用的 | 给外部应用访问 M365 用的，**同一个门户** |
| 安全组（Security Group） | CRM 团队关联的安全组 | Entra ID 的 Group，可以关联 Teams、SharePoint |
| 服务主体（Service Principal） | 应用注册后在租户里的"影子" | 完全相同 |
| 管理员同意（Admin Consent） | 给应用授 CRM 权限 | 给应用授 M365 权限（如 Mail.Read） |

**关键认知**：你不需要学新的身份系统，只需要理解同一个 Entra ID 在不同服务里的权限表达方式不同。

## 2. OAuth 2.0 认证流

### 2.1 两种主要认证场景

| 场景 | OAuth 流 | 类比 D365 | 适用 |
|---|---|---|---|
| **委托权限**（Delegated） | 授权码流（Authorization Code） | 用户登录 CRM 后前端 JS 调 Web API | 有用户登录的 Web/移动应用 |
| **应用权限**（Application） | 客户端凭据流（Client Credentials） | 插件里用 System 组织服务 | 后台服务、守护进程、无人值守任务 |

### 2.2 授权码流（有用户登录）

```
用户浏览器                你的应用后端              Entra ID              M365 资源
    │                        │                       │                      │
    │  1. 点击"登录"         │                       │                      │
    │───────────────────────>│                       │                      │
    │                        │  2. 重定向到 Entra     │                      │
    │  3. 跳转到登录页        │<──────────────────────│                      │
    │<───────────────────────│                       │                      │
    │  4. 用户输入凭据        │                       │                      │
    │───────────────────────────────────────────────>│                      │
    │                        │                       │  5. 验证成功           │
    │  6. 重定向回你的应用    │                       │  带 authorization_code│
    │<───────────────────────────────────────────────│                      │
    │                        │  7. 用 code 换 token   │                      │
    │                        │──────────────────────>│                      │
    │                        │  8. 返回 access_token │                      │
    │                        │<──────────────────────│                      │
    │                        │  9. 用 token 调 API    │                      │
    │                        │──────────────────────────────────────────────>│
    │                        │  10. 返回数据          │                      │
    │                        │<──────────────────────────────────────────────│
```

### 2.3 客户端凭据流（无用户，后台服务）

```csharp
// C# 示例：后台服务用应用身份调 Graph API
using Azure.Identity;
using Microsoft.Graph;

// 用应用注册的 client_id + client_secret 获取令牌
var credential = new ClientSecretCredential(
    tenantId: "your-tenant-id",
    clientId: "your-client-id",
    clientSecret: "your-client-secret"
);

var graphClient = new GraphServiceClient(credential);

// 以应用身份读取所有用户（需要 User.Read.All 应用权限）
var users = await graphClient.Users.GetAsync();
```

**和 D365 对照**：
- D365 里用 `IClientOrganizationService` 做无用户调用
- M365 里用 `ClientSecretCredential` + `GraphServiceClient` 做无用户调用
- 原理一样：用应用凭据而非用户凭据认证

## 3. 单点登录（SSO）实现

### 3.1 SSO 的含义

用户在 D365 CRM 登录后，访问 M365 相关应用（Teams、SharePoint、Power Apps）时不需要再次登录——因为它们共享同一个 Entra ID 会话。

### 3.2 不同场景的 SSO

| 场景 | SSO 实现方式 |
|---|---|
| Web 应用（React/Angular）访问 Graph | MSAL.js（Microsoft Authentication Library）——自动处理令牌刷新和 SSO |
| SPFx Web 部件访问 Graph | SPFx 内置 `MSGraphClient`——自动获取当前用户的 Graph 令牌 |
| Teams 选项卡应用访问 Graph | Teams SSO——`authentication.getAuthToken()` 获取令牌，后端换 Graph 令牌 |
| 桌面应用（WPF/WinForms）访问 Graph | MSAL.NET——支持交互式登录 + 令牌缓存实现 SSO |
| 后台服务访问 Graph | 没有 SSO 概念——用客户端凭据流直接获取应用令牌 |

### 3.3 MSAL.js 示例（Web 应用）

```javascript
import { PublicClientApplication } from '@azure/msal-browser';

const msalConfig = {
    auth: {
        clientId: 'your-client-id',
        authority: 'https://login.microsoftonline.com/your-tenant-id',
        redirectUri: 'http://localhost:3000'
    }
};

const msalInstance = new PublicClientApplication(msalConfig);

// 登录并获取 Graph API 的 access token
const loginResponse = await msalInstance.loginPopup({
    scopes: ['User.Read', 'Mail.Read']  // 请求的 Graph 权限
});

// 后续调用自动使用缓存的令牌（SSO 效果）
const tokenResponse = await msalInstance.acquireTokenSilent({
    scopes: ['User.Read']
});

// 用令牌调 Graph
const response = await fetch('https://graph.microsoft.com/v1.0/me', {
    headers: { Authorization: `Bearer ${tokenResponse.accessToken}` }
});
const user = await response.json();
```

### 3.4 SPFx 内置 Graph 客户端

```typescript
// SPFx Web 部件里调 Graph——不需要手动管理令牌
import { MSGraphClient } from '@microsoft/sp-http';

const client = await this.context.msGraphClientFactory.getClient();
const messages = await client
    .api('/me/messages')
    .select('subject,from,receivedDateTime')
    .top(10)
    .get();
```

**对比 D365**：
- D365 里前端调 Web API 用 `Xrm.WebApi`，自动带认证
- SPFx 里调 Graph 用 `MSGraphClient`，也是自动带认证
- 体验几乎一样

## 4. 权限管理

### 4.1 权限类型对照

| 维度 | D365（Dataverse） | M365（Graph） |
|---|---|---|
| 权限粒度 | 表级 + 字段级安全配置文件 | API 级 scope（如 `Mail.Read`、`User.ReadWrite.All`） |
| 委托权限 | 用户的安全角色决定能做什么 | 用户权限 ∩ 应用权限——两者都要有 |
| 应用权限 | 插件默认以 System 身份运行 | 应用权限（Application permission）——需管理员同意 |
| 管理员同意 | 在 Power Platform 管理中心配置 | 在 Entra 管理门户 → 企业应用 → 同意设置 |

### 4.2 Graph API 常见权限

| 权限名 | 类型 | 说明 | 类比 Dataverse |
|---|---|---|---|
| `User.Read` | 委托 | 读登录用户自己的资料 | 读自己的 SystemUser 记录 |
| `User.Read.All` | 委托/应用 | 读所有用户资料 | 读所有 SystemUser（需管理员权限） |
| `Mail.Read` | 委托/应用 | 读邮件 | 无直接类比（Dataverse 不管邮件） |
| `Mail.Send` | 委托/应用 | 代用户发邮件 | 无直接类比 |
| `Sites.Read.All` | 委托/应用 | 读 SharePoint 站点 | 读 Dataverse 笔记附件 |
| `Group.ReadWrite.All` | 委托/应用 | 读写所有 M365 组 | 管理 Dataverse 团队 |
| `Calendars.ReadWrite` | 委托/应用 | 读写日历 | 读写 appointment 实体 |

### 4.3 最小权限原则

```
❌ 反模式：给应用授 *.All 权限然后在前端过滤
✅ 正确：只授应用实际需要的权限

场景：只需要显示当前用户信息
❌ User.Read.All
✅ User.Read（只读登录用户自己）

场景：只需要发邮件通知
❌ Mail.ReadWrite（能读能写所有邮件）
✅ Mail.Send（只能发邮件）
```

## 5. 跨系统调用的令牌处理

### 5.1 同一个令牌，多个资源

Entra ID 颁发的 access token 是**资源特定**的——一个令牌只能用于一个资源（Graph 或 Dataverse），不能通用。

```
获取 Graph 令牌 → 只能调 graph.microsoft.com
获取 Dataverse 令牌 → 只能调 yourorg.crm.dynamics.com
```

### 5.2 同时调 Graph 和 Dataverse

如果你的应用需要同时访问两个系统：

```javascript
// 方案 1：分别获取令牌
const graphToken = await msalInstance.acquireTokenSilent({
    scopes: ['https://graph.microsoft.com/.default']
});

const dataverseToken = await msalInstance.acquireTokenSilent({
    scopes: ['https://yourorg.crm.dynamics.com/.default']
});

// 方案 2：后端统一获取（推荐）
// 前端只发一个请求给后端，后端用 client credentials 分别获取两个系统的令牌
```

### 5.3 On-Behalf-Of（OBO）流

当前端应用需要调后端 API，后端 API 再调 Graph/Dataverse 时，用 OBO 流传递用户身份：

```
前端（有用户令牌）
   ↓  调后端 API，带上用户的 access_token
后端 API
   ↓  用 OBO 流，把用户令牌换成后端调 Graph 的令牌
Graph API / Dataverse
   ↓  看到的还是用户身份，不是后端应用身份
```

```csharp
// 后端 C# 代码：用 OBO 流获取 Graph 令牌
var credential = new OnBehalfOfCredential(
    tenantId: "your-tenant-id",
    clientId: "your-client-id",
    clientSecret: "your-client-secret",
    userAssertion: userAccessToken  // 前端传来的用户令牌
);

var graphClient = new GraphServiceClient(credential);
// 后续调用以用户身份执行
```

## 6. 条件访问策略（Conditional Access）

管理员可以配置条件访问策略，控制什么情况下允许访问：

| 条件 | 示例 |
|---|---|
| 用户/组 | 只允许销售组访问 CRM + SharePoint |
| 位置 | 公司网络内允许，外部网络需要 MFA |
| 设备 | 只有公司管理的设备才能访问 |
| 应用 | 只允许特定应用注册访问 |
| 风险级别 | 高风险登录需要额外验证 |

**对开发者的影响**：
- 你的应用可能需要处理 MFA 挑战（MSAL 会自动处理）
- 测试时注意条件访问策略可能阻止你的应用注册
- 如果测试被拦截，联系管理员把你的应用加入白名单

## 7. 本章小结

- D365 和 M365 共享同一个 Entra ID——身份体系完全统一
- 两种认证流：授权码（有用户）和客户端凭据（无用户）
- SSO 通过 MSAL 库自动实现——用户登录一次即可访问所有授权应用
- 权限管理要遵循最小权限原则
- 跨系统调用需要分别获取令牌，或用 OBO 流传递用户身份
- 条件访问策略可能影响应用访问——开发和测试时要注意
