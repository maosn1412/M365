# 11 · Outlook 客户信息侧边栏方案评估

> 评估日期：2026-11-09
> 需求：销售在 Outlook 中处理客户邮件时，点击按钮打开右侧任务窗格，查看或创建第三方 SaaS/ERP 中的客户记录，并随邮件内容变化同步刷新。
> 结论：**可实现**。推荐"Outlook 加载项任务窗格 + BFF 中间层 + ERP API"方案；不建议把 ERP 页面直接 iframe 进窗格作为主方案。

## 1. 需求描述

### 1.1 业务场景

1. 销售在 Outlook 收到新客户邮件（询盘、转介绍、表单通知等）
2. 点击邮件功能区按钮"客户360"
3. 右侧任务窗格显示该客户在 ERP 中的信息；若不存在，则提供预填的新建表单
4. 销售在窗格内确认后创建客户，窗格立即显示新客户信息
5. 撰写邮件时输入客户邮箱/名称，窗格同步匹配并展示客户

> 说明：本文按"客户/联系人主数据"描述，需求中的"新建用户"指在 ERP 中新建客户或联系人记录。

### 1.2 本期边界

| 项目 | 范围 |
|---|---|
| Outlook 客户端 | Outlook Web、新版 Outlook（不含经典 Windows / Mac / 移动端） |
| 目标系统 | 第三方 SaaS/ERP（具体产品待定） |
| 交付阶段 | 先原型（侧加载 + mock API），再对接真实 ERP |
| 不在范围 | 邮件自动归档、完整 CRM 功能、移动端适配 |

## 2. 可行性结论

### 2.1 分项判断

| 能力 | 结论 | 说明 |
|---|---|---|
| 按钮 + 右侧任务窗格 | 完全可行 | Outlook 加载项标准能力；Web/新版支持任务窗格固定（pinnable） |
| 读取邮件中的客户信息 | 可行 | Office.js 可读 from / recipients / subject / body / 附件 |
| 窗格内展示第三方系统页面 | 有条件可行 | 最大不确定项：SaaS 是否允许 iframe（X-Frame-Options / CSP frame-ancestors）；第三方 Cookie 受限会导致嵌入页面登录态失效 |
| 匹配/新建客户并回显 | 可行 | 通过 BFF 调 ERP API；需定义匹配键与重复检测规则 |
| 随邮件变化同步刷新 | 可行 | 阅读模式用 `ItemChanged`；撰写模式用 `RecipientsChanged`；正文变化无事件，需防抖轮询 |

### 2.2 方案对比

| 方案 | 做法 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| A · 直接 iframe ERP 页面 | 窗格内嵌现有 ERP 页面 | 复用现有 UI，开发量小 | 多数 SaaS 拒绝被嵌入；第三方 Cookie/SSO 导致登录失败；窄窗格布局不可控 | 仅当 ERP 明确支持嵌入且 SSO 可用时作为增强 |
| B · BFF + 自建窗格 UI | 窗格用 React 自绘，后端调 ERP API | 安全可控、体验一致、可做匹配/新建 | 需要 ERP API 与字段映射 | **推荐主方案** |
| C · 低代码卡片 | Power Automate 触发，窗格展示自适应卡片 | 上手快、无需前端托管 | 交互弱，难以实时匹配和创建 | 备选（只读通知场景） |

## 3. 目标架构

```
Outlook Web / 新版 Outlook
  [按钮：客户360]
    └─ 任务窗格（HTTPS 页面，React + Office.js）
         │ 读取邮件上下文 + SSO token（NAA/MSAL）
         ▼
BFF 中间层（Azure Functions / App Service）
  · 校验 token、字段抽取、客户匹配、防重复、日志
         │ ERP API（服务端凭据或 OAuth）
         ▼
第三方 SaaS/ERP（查询/创建客户）
```

### 3.1 组件职责

| 组件 | 职责 | 关键约束 |
|---|---|---|
| 任务窗格 | 读取邮件上下文、展示客户卡片/新建表单、接收用户操作 | 宽度约 320px 起；只持有用户令牌，不持有 ERP 凭据 |
| BFF 中间层 | 验证 JWT、抽取客户字段、匹配与防重、调用 ERP、审计日志 | 凭据存 Key Vault；超时、限流、重试、幂等 |
| 第三方 ERP | 客户主数据唯一来源 | API 能力、速率限制、字段必填与重复规则 |
| Entra ID | 用户身份与应用授权 | 单租户应用注册、管理员同意、Expose an API |

## 4. 关键交互流程

### 4.1 读信匹配（命中）

1. 用户点击"客户360"，任务窗格打开
2. 窗格读取 `item.from.emailAddress`、`subject`、`body`（纯文本）
3. 调用 BFF `/customers/match`，按优先级匹配：联系人邮箱 → 客户域名 → 税号/客户编号 → 名称模糊
4. 命中唯一客户 → 展示客户卡片（名称、负责人、最近订单、ERP 深链）

### 4.2 读信匹配（未命中）→ 新建

1. 无匹配或多匹配 → 展示"未找到/请选择"状态
2. 用抽取到的字段预填新建表单（公司名、联系人、邮箱、电话等）
3. 用户核对并确认 → BFF 执行重复检测 → 调 ERP 创建
4. 创建成功 → 窗格切换为新建客户的详情，并保留 ERP 深链

> 不建议静默自动创建：邮件中的公司名/联系人可能存在歧义，必须经过用户确认。

### 4.3 撰写模式同步

1. 收件人变化 → `RecipientsChanged` 触发重新匹配
2. 附件增删 → `AttachmentsChanged` 触发重新解析
3. 正文变化 → **没有对应事件**，采用 3–5 秒防抖轮询 `body.getAsync`，或提供手动刷新按钮
4. 窗格内新建客户后，可提供"把客户信息插入邮件"的可选操作（需 `ReadWriteItem` 权限）

### 4.4 同步机制

| 场景 | 事件/机制 | 最低要求集 | 备注 |
|---|---|---|---|
| 阅读模式切换邮件 | `Office.EventType.ItemChanged` | Mailbox 1.5 | 依赖宿主支持固定窗格（Web/新版） |
| 撰写模式收件人变化 | `Office.EventType.RecipientsChanged` | Mailbox 1.7 | 触发重新匹配 |
| 撰写模式附件变化 | `Office.EventType.AttachmentsChanged` | Mailbox 1.8 | 触发附件解析 |
| 撰写模式正文变化 | 无事件 | — | 防抖轮询或手动刷新 |
| 窗格固定 | `SupportsPinning` | Mailbox 1.5 | 阅读模式为主 |

## 5. 技术选型建议

| 层 | 建议 | 理由 |
|---|---|---|
| 加载项形态 | Office 加载项（XML 清单） | 兼容性最好；统一清单可作为后续演进 |
| 前端 | React + Fluent UI + Office.js | 与本仓库 Teams Tab 技术栈一致；Fluent UI 适配窄窗格 |
| 认证 | NAA（MSAL.js）+ Entra 应用注册 | Web/新版 Outlook 推荐；避免旧版 SSO 的宿主差异 |
| BFF | .NET（Azure Functions / ASP.NET Core）或 Node | 按团队技能选择；与 D365 背景一致优先 .NET |
| ERP 凭据 | Key Vault 托管 + 服务端调用 | 前端绝不接触 ERP 密钥 |
| 部署 | M365 管理中心 Integrated Apps | 集中分发、按组授权、可回收 |

## 6. 限制与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| ERP 拒绝 iframe（X-Frame-Options / CSP） | 嵌入方案不可用 | 采用 BFF + 自建 UI 主方案；嵌入仅作增强 |
| 第三方 Cookie / SSO 限制 | 嵌入页面登录态失效 | 放弃"嵌入已有页面"，改用带令牌的 API 调用 |
| ERP API 不开放创建或限流严格 | 无法新建/体验差 | 提前向厂商确认；缓存、限流、批量接口 |
| 自由文本抽取错误 | 建错客户或重复客户 | 人工确认；置信度阈值；创建前重复检测 |
| 邮件内容合规 | 数据出境/留存违规 | 最小化传输、脱敏、合规评审后再接真实邮件 |
| 管理员同意与分发审批慢 | 上线延期 | 提前走审批；侧加载先行试点 |
| 撰写正文无变化事件 | 同步不及时 | 防抖轮询 + 手动刷新 + 明确状态提示 |
| 权限申请过大 | 安全评审受阻 | 默认 `ReadItem`；确需回写才用 `ReadWriteItem` |

## 8. 验收标准

### 8.1 功能验收

- 阅读/撰写模式下点击"客户360"可在 1 秒内打开右侧任务窗格
- 邮件命中唯一客户时，3 秒内展示客户卡片，包含名称、负责人、最近订单与 ERP 深链
- 未命中时展示预填表单；必填校验通过且用户确认后才创建；创建成功 2 秒内回显新客户
- 切换邮件后窗格自动刷新，不残留上一封邮件的客户信息
- 撰写模式下收件人变化触发重新匹配；正文变化在 5 秒内反映
- 创建失败、ERP 超时、无权限均有明确提示与重试入口；重复提交不会产生重复客户

### 8.2 非功能验收

- 加载项权限最小化（默认 `ReadItem`），清单通过 `office-addin-manifest validate`
- 前端无 ERP 凭据；BFF 校验令牌签名、受众、权限范围
- 日志记录用户、邮件 itemId、操作、结果；不记录完整邮件正文
- 支持 Integrated Apps 集中部署与按组授权

## 9. 实施阶段建议

| 阶段 | 内容 | 预估 |
|---|---|---|
| P0 原型 | 侧加载加载项；按钮打开窗格；读取 from/subject/body；mock API 匹配；客户卡片 | 1–2 天 |
| P1 集成 | Entra 应用注册 + NAA；BFF 校验；ERP 沙箱查询/创建；防重与幂等；撰写模式同步 | 3–5 天 |

## 10. 建议优先确认的 5 个问题

1. ERP 具体产品与版本是什么？是否开放客户查询/创建 API 与沙箱环境？
2. ERP 的认证方式是什么？ERP 账号与 M365 账号如何映射？
3. 是否允许页面被 iframe 嵌入（CSP / X-Frame-Options）？是否支持客户详情深链？
4. 客户的唯一键、重复检测规则与必填字段是什么？
5. 新客户信息通常以什么形式出现在邮件中（固定模板/正文/附件）？邮件内容传给 ERP 是否合规？
